# 从零制作 COD 乙女向 AIRP 文游

> 视频教程口播稿 + 实操流程 + 可复制提示词  
> 案例参考：[《里世界》GitHub 项目](https://github.com/w1990709164-bot/Ura)

## 开场

大家好，我是观南。

今天这个视频主要是讲解如何自制 Airp 文游。

俗话说，授人以鱼，不如授人以渔。尽管当下的创作环境比从前多了不少恶意与杂音，但我始终相信，仍然有很多人愿意为了热爱而坚持创作，也希望大家都能找到适合自己的表达方式与创作出口。

首先是关于 Airp 是什么。

简单来说，就是让 AI 来扮演一个虚拟世界里的角色或主持人，比如跑团里的 DM；你作为玩家可以自由地探索剧情、和角色互动。因为它基于大语言模型，理论上玩家可以做出任何选择，体验高自由度、不受固定剧本完全限制的文字冒险。

像我之前制作的《里世界》《白塔》《交火心跳》等，都是 Airp。

不过，AIRP 并不等于“给 AI 一张角色卡，再套一个聊天框”。一个比较完整的 AIRP 游戏，至少需要五个部分：世界规则、角色人格、玩家身份、游戏循环，以及 AI 的输出协议。今天我会以《里世界》的结构为例，从构思开始，一直讲到如何把需求交给 AI，最后做出可以运行、可以存档、也可以继续扩充的网页文游。

> 画面建议：依次展示《里世界》总入口、创建角色页、地图、角色对话、档案与任务界面。

## 第一部分：先想游戏体验，不要急着写代码

很多人第一次找 AI 做游戏，会直接说：“帮我做一个 COD 乙女游戏。”这句话方向没错，但信息远远不够。AI 不知道玩家是谁，不知道角色为什么会和玩家相遇，也不知道一轮游戏到底要做什么。它只能自行补全，而自行补全通常就是最容易俗套和失控的部分。

所以第一步不是写代码，而是用一句话说清楚你的游戏。

这个句子可以套用下面的公式：

> 玩家身份 + 所处环境 + 核心行动 + 情感目标 + 主要压力

比如《里世界》可以概括成：

> 玩家以自定义身份进入多个 COD 阵营共同驻扎的联合基地，在训练、任务和日常生活中自由行动，与不同角色逐步建立关系，同时面对阵营立场、工作职责和个人选择带来的压力。

这句话决定了后面所有系统：

- “联合基地”决定地图和阵营结构；
- “自定义身份”决定捏人页；
- “自由行动”决定时间与行动点；
- “逐步建立关系”决定好感阶段与记忆；
- “任务和阵营压力”决定游戏不只是谈恋爱，还要有职业线与世界事件。

在找 AI 之前，建议先填完这张最小企划表：

| 项目 | 要回答的问题 | 《里世界》式示例 |
|---|---|---|
| 一句话概念 | 玩家在什么地方做什么？ | 联合基地中的自由探索与多角色关系发展 |
| 核心情绪 | 希望玩家主要感到什么？ | 危险环境中的信任、克制和暧昧 |
| 玩家身份 | 玩家凭什么进入这个世界？ | 医疗、情报、作战或后勤人员 |
| 日常循环 | 每一回合重复什么？ | 选地点—行动—互动—结算—推进时间 |
| 长线目标 | 玩十几回合后追求什么？ | 晋升、完成事件线、解锁关系阶段 |
| 失败与代价 | 选择是否有后果？ | 体力消耗、任务失败、关系变化、错过事件 |
| AI 的职责 | 哪些内容需要临场生成？ | 对话、短叙事、选项与事件反馈 |
| 程序的职责 | 哪些规则必须稳定？ | 数值、时间、存档、触发条件、页面切换 |

这里最重要的一条原则是：**让程序负责确定性，让 AI 负责变化。**

钱有多少、今天第几天、是否已经行动、好感加了几点，这些不能让 AI 随口决定后又忘掉，应该由代码记录。角色说什么、怎样回应玩家、某次任务现场出现什么细节，则可以交给 AI 生成。这样既有自由度，又不会玩几轮就崩坏。

## 第二部分：世界观不是背景简介，而是运行规则

世界观最常见的问题是写得很长，却不能指导游戏。比如“这里是一座神秘基地，暗流涌动”，听起来很有氛围，但 AI 仍然不知道谁能进入武器库、不同阵营为什么共处、平时是否能离开基地、任务失败有什么影响。

一个适合 AIRP 的世界观，建议分成六层。

### 1. 时空与现实程度

先确定时代、地点以及现实规则。

- 是现代军事世界，还是近未来、末日、校园、哨向或无限流？
- 是否存在超自然力量？
- 武器、医疗、通讯和法律遵循什么标准？
- 原作剧情是完全继承、部分借用，还是平行世界？

COD 乙女向同人尤其要先选时间线。不同作品和角色未必处于同一时期。如果想让 Ghost、Keegan、König 等角色同场，最好直接声明这是“平行世界的联合行动基地”，而不是强行声称完全遵循原作时间线。这样既保留人物辨识度，也给二创留出合理空间。

### 2. 核心场所

地图不是装饰，它决定玩家能做什么。《里世界》的地点包含公共休息区、食堂、训练场、靶场、医务室、情报室、档案室、通讯室、各阵营驻地以及附近小镇。每个地点都天然对应一种玩法：

- 训练场：训练、能力成长、偶遇；
- 医务室：治疗、照顾、伤情事件；
- 情报室：调查、解谜、阵营信息；
- 食堂和休息区：轻松日常、群像互动；
- 阵营驻地：更私密、需要权限或关系门槛；
- 小镇：采购、约会、支线和脱离基地的生活感。

设计地图时，不要只列地名，要给每个地点写三项：视觉气味或声音、常驻人物、可触发行为。

### 3. 阵营与利益

阵营不能只是角色名字下面的一行标签。每个阵营至少需要：公开目标、行事方式、掌握的资源、与其他阵营的关系，以及对玩家的初始态度。

可以用下面这张表：

| 阵营 | 公开目标 | 优势资源 | 行事风格 | 内部矛盾 | 玩家切入点 |
|---|---|---|---|---|---|
| TF141 | 完成联合任务 | 指挥与实战经验 | 纪律、任务优先 | 信任门槛高 | 被临时调入或提供专业支持 |
| Ghosts | 侦察与隐蔽行动 | 情报、追踪 | 安静、协同 | 对外来者谨慎 | 联合侦察、医疗或情报交换 |
| Chimera | 合同任务 | 灵活人脉与行动力 | 务实、利益导向 | 忠诚与报酬冲突 | 合同对接、黑市线索 |
| KorTac | 执行独立战术目标 | 人员与装备 | 强硬、封闭 | 与其他队伍互不完全信任 | 共同训练或危机合作 |

阵营之间最好不要简单分为好人和坏人。真正能支持长线剧情的，是“目标暂时一致，但方法和代价不同”。这样玩家的选择才会产生立场，而不是只有正确答案。

### 4. 日常制度

把世界写成能生活的地方：一天有几个时间段？工作日和周末有什么区别？玩家如何领任务、领取报酬、购买物品、进入限制区域？角色不与玩家互动时在做什么？

《里世界》把一天拆成上午、中午、下午、晚上，并用地点、体力、金钱、能力、心情等状态形成循环。这个结构很适合新手，因为它明确又容易扩展。

### 5. 矛盾来源

剧情不等于不断发生枪战。乙女向的矛盾可以同时来自三层：

- 外部：任务、敌对势力、情报泄露、资源不足；
- 人际：阵营差异、职业保密、误解、竞争与信任；
- 内部：角色创伤、职责和私人愿望冲突，玩家自身的立场选择。

最好为每层准备三到五个“事件种子”，而不是提前写死完整结局。事件种子只规定起因、参与者、信息和后果，具体过程交给 AI 与玩家共同展开。

### 6. 边界和基调

提前写清楚内容边界，例如是否允许角色死亡、是否允许黑化、亲密内容到什么程度、玩家是否拥有完全拒绝权、是否禁止囚禁、跟踪、财务控制、羞辱或非自愿情节。

这不是削弱戏剧性，而是在告诉 AI：冲突应该从哪里产生，不能靠什么廉价手段制造。危险可以来自任务，张力可以来自立场和克制，不需要用侵犯玩家意志来代替剧情。

## 第三部分：角色卡要写“行为逻辑”，不只是形容词

“冷漠、强大、占有欲强、只对你温柔”不是完整人设，因为这些词没有说明角色在具体场景中会怎么做。AI 很容易把所有冷淡角色写成沉默，把所有暧昧角色写成压低嗓音、逼近墙角。

更可靠的角色卡可以分成八项：

1. **公开身份**：姓名、年龄段、国籍、军衔、阵营、职责；
2. **核心驱动力**：他最想守住什么，最害怕失去什么；
3. **价值排序**：任务、队友、原则、自由、感情，谁排在前面；
4. **能力与局限**：擅长什么，在哪些事上会失败；
5. **社交分层**：对陌生人、同事、信任者和恋人的差异；
6. **压力反应**：受伤、愤怒、嫉妒、任务失败时如何表现；
7. **语言指纹**：句长、用词、口音、是否说脏话、沉默频率；
8. **禁止偏移**：绝不会做什么，以及最容易被 AI 写歪成什么。

以一个偏寡言的侦察手为例，不要只写“冷静、温柔、靠谱”，可以写成：

> 他优先保证任务成功，但不会把队友当成耗材。面对新手时先给一次清晰指导，再观察执行能力；如果对方继续失误，他会直接接管，不会长篇训斥。关心主要通过提前检查装备、调整站位和记住细节表现，很少直接说安慰话。被质疑专业能力时，他会用结果回应，而不是提高音量。

这段人设之所以好用，是因为 AI 能从中推导行为。

### 让不同男主真正有区别

可以设计同一场景测试所有角色。例如“玩家带伤隐瞒并准备继续出任务”：

- Ghost 可能先确认伤势和任务风险，用极短的句子要求重新评估；
- Keegan 可能默默接过部分装备，给出实际方案，同时观察玩家是否还能胜任；
- Krueger 可能先讽刺玩家不划算的逞强，再从合同和生存角度阻止；
- König 的日常焦虑和战斗状态可能产生明显反差；
- Nikto 可能几乎不解释，只把医疗包放到玩家手边并守住出口；
- Zimo 可能先用轻松口吻套出真实伤情，确认后立刻切换成任务语气。

如果所有人都只是“皱眉、压低声音、说你怎么这么不听话”，说明角色卡没有真正控制输出。

### 关系阶段也要改变行为，而不只是称呼

《里世界》使用“陌生人—普通同事—熟识—信任—暧昧—恋人”的阶段结构。每一级最好分别规定：

- 主动交流频率；
- 可透露的信息；
- 肢体距离和私人空间；
- 是否会主动邀请；
- 冲突后的修复方式；
- 特殊事件的解锁条件。

例如陌生阶段不该因为一次送礼就立刻交代全部创伤；信任阶段的变化可以是愿意把后背交给玩家、分享任务判断、主动请求协助；暧昧阶段才逐渐出现对玩家区别于他人的关注。这样感情线才像“关系发展”，而不是好感数字换了一个标签。

## 第四部分：玩家设定不是附属品

乙女游戏很容易把玩家写成一块空白，但 AIRP 的自由输入会不断要求世界回应玩家。如果只填写名字，AI 就会随时编造玩家的外貌、能力和经历，甚至替玩家决定情绪。

建议让玩家至少设置：

- 代号与姓名；
- 身份或职位；
- 外貌，可选；
- 性格或表达习惯，可选；
- 专长与短板；
- 与基地或阵营的来历；
- 不希望 AI 代写的内容；
- 内容边界。

其中最关键的是身份。身份必须能带来玩法差异，而不是一张无效标签。

例如：

- 医疗人员更容易接触伤病、病历和照顾事件，但作战能力有限；
- 情报人员能进入档案室并分析线索，但可能受到保密限制；
- 作战人员能参加外勤，却要承担更高体力与失败风险；
- 后勤人员掌握资源、调度和广泛人际网络，能看到基地的另一面。

还要明确一条系统规则：**AI 可以描写环境和 NPC，但不能替玩家决定思想、感受、台词和关键行动。**它可以写“门后传来脚步声”，不能擅自写“你害怕得扑进他怀里”。玩家的主体性是互动叙事成立的基础。

## 第五部分：把玩法设计成一个可重复循环

AIRP 的自由度越高，越需要一个清楚的游戏循环，否则玩家很快会不知道该做什么。

一个适合初版的循环是：

> 查看状态 → 选择地点 → 选择行动或角色 → AI 生成互动 → 程序结算数值 → 记录关键记忆 → 推进时间 → 检查事件触发

《里世界》中，玩家可以移动到不同地点，与在那里的人物展开有限轮次对话。AI 返回角色动作、外语台词、中文翻译、三类选项和好感变化；程序再更新关系、体力和记忆。这个拆法很值得借鉴。

### 推荐保留的基础系统

#### 时间系统

一天四个时间段就足够：上午、中午、下午、晚上。每次主要行动消耗一个时间段，晚上结算并进入下一天。限制能制造取舍，也能控制 API 成本。

#### 地图与人物行程

角色不应该永远等在同一个地方。可以给每人设置基础日程，再用任务或天气临时覆盖。玩家偶遇一个正在生活的角色，比点击通讯录点名聊天更有世界感。

#### 状态系统

初版不要堆十几种数值。建议只保留三到五项真正参与判断的状态，例如体力、能力、金钱、心情和职位等级。每个数值都要回答：怎样增加、怎样减少、会影响什么。

#### 关系系统

不要把好感当成唯一真相。可以用“关系阶段 + 当前好感 + 关键旗标”组合。例如：

- `trust_rescue_completed`：共同完成救援；
- `knows_real_name`：对方知道玩家真名；
- `conflict_unresolved`：上次争执尚未解决；
- `gave_personal_token`：收到私人纪念物。

数字控制节奏，旗标保留故事意义。

#### 任务与事件系统

任务最好分为三类：

- 固定事件：重要主线，触发条件与结果明确；
- 半随机事件：从事件池抽取，AI 生成过程细节；
- 自由互动：玩家自填行动，AI 根据当前状态回应。

这样既不会完全失控，也不会像传统选项游戏一样只能走预设路线。

#### 记忆系统

不要把全部聊天记录永久塞给 AI。内容越长，成本越高，也越容易抓错重点。可以保留：

- 最近几轮原始对话；
- 最近十条世界事件；
- 每个角色一份关系摘要；
- 永久关键旗标。

每次结束行动后，让程序或 AI 把本轮压缩成一两条事实，例如：“第 3 天，玩家在靶场替 Keegan 校正装备；对方认可其专业判断。”记忆要写事实，不要写空泛感想。

### 三类选项的作用

《里世界》用温线、锐线和暗线提供选择，同时允许玩家自填：

- 温线：理解、关心、建立连接；
- 锐线：质疑、对抗、推动冲突；
- 暗线：观察、试探、搜集信息；
- 自填：真正的自由输入。

这不是三种“正确程度”，而是三种叙事方向。不要让温线永远加好感、锐线永远扣好感。某些角色更尊重直接质疑，某些任务中暗线选择可能更有效。只有结果与人物价值观相关，选项才有意义。

## 第六部分：剧情不要写成一条线，要写成触发网络

AIRP 不适合先写几十万字完整剧本，再要求 AI 严格复述。更适合的方式是设计“锚点剧情”。

每个事件用一张事件卡：

```text
事件名：失踪的行动档案
触发条件：第 3 天后；玩家去过档案室；当前无主线任务
参与角色：玩家、情报负责人，可随机加入一名相关角色
已知事实：档案在交接后失踪；门禁没有暴力破坏
隐藏真相：文件被内部人员临时调包，动机尚未确定
玩家目标：寻找线索并决定向谁报告
可变过程：搜索方式、怀疑对象、角色冲突由 AI 根据行动生成
硬性限制：AI 不得提前泄露真相；证据不足时不能直接定罪
结果：记录玩家选择的阵营、获得线索旗标、改变相关人物信任
```

一条长线剧情可以拆成：开端锚点、两到三个调查锚点、一次不可逆选择、后果事件和结局判定。AI 负责锚点之间的道路，代码负责确认哪些锚点已经发生。

恋爱线也可以如此设计：初次合作、第一次私人信息交换、价值观冲突、主动信任、关系确认。不要把“告白”仅仅设置为好感满 300 自动弹出。最好同时要求关键旗标和一次玩家主动选择。

### 让群像世界继续运转

角色除了恋爱线，还应该拥有：

- 自己正在执行的任务；
- 与其他角色的既有关系；
- 不因玩家存在而消失的职责；
- 会拒绝玩家的合理时刻；
- 玩家不在场时也可能发生的事件。

角色会忙、会离开、会有不同意见，反而更容易让玩家相信这段关系。

## 第七部分：怎样和 AI 沟通，才能真的得到游戏

最有效的方法不是一次让 AI 做完整项目，而是分阶段交付。每一阶段都要告诉 AI：背景、任务、硬约束、输入材料、输出格式和验收标准。

### 第一步：让 AI 当策划，不写代码

可以复制这段：

```text
你现在是互动叙事游戏策划。我要制作一款浏览器运行的 COD 乙女向 AIRP 文字游戏。

核心概念：玩家以自定义职业进入一个平行世界联合基地，在日常、任务和阵营事件中与多个角色建立关系。
核心体验：危险职业环境中的信任、克制、群像生活与慢热情感。
目标平台：手机浏览器优先，同时适配电脑。

请先不要写代码。请输出：
1. 一句话玩法；
2. 每回合游戏循环；
3. 世界运行规则；
4. 阵营关系表；
5. 地点及每个地点的玩法；
6. 玩家身份方案及差异；
7. 需要由代码保存的状态字段；
8. AI 负责生成与禁止决定的内容；
9. 一个只包含必要功能的 MVP 范围；
10. 可能失控的设计点和修正方式。

不要擅自增加超自然设定，不要替玩家决定心理或行动。信息不足时先列出假设。
```

拿到结果后不要直接说“很好，开始做”。逐项修改，直到企划与你想要的体验一致。尤其检查 AI 有没有擅自加入你不喜欢的套路。

### 第二步：单独制作角色圣经

```text
请为以下角色制作“可执行角色卡”。角色卡不是文案，要能直接约束大语言模型的表演。

原始资料：[粘贴你整理并核对过的角色资料]
本作设定：[粘贴平行世界与阵营关系]

每个角色必须包含：
- 公开身份与职责
- 核心驱动力和价值排序
- 能力、局限与秘密
- 对陌生人/同事/信任者/恋人的行为差异
- 平静、压力、受伤、愤怒、嫉妒时的反应
- 语言节奏、常用语言、禁用表达
- 关系各阶段允许和不允许的行为
- 三个能区分该角色的情境测试
- 最容易出现的 OOC 方式及纠偏规则

要求：角色必须拥有独立生活，不围着玩家转；不使用通用霸总措辞；不把外貌描写当作性格；不编造为官方事实的经历标注为本作二创设定。
```

### 第三步：先让 AI 设计数据结构

```text
根据已经确认的策划案，请先设计前端游戏状态结构，不写 UI。

技术范围：原生 HTML、CSS、JavaScript；无需构建工具；浏览器本地存档。
请设计：
- GameState
- CharacterState
- WorldEvent
- MemorySummary
- SaveData
- AIResponse

要求：
1. 静态角色资料与运行时状态分开；
2. 好感数字、关系阶段和关键旗标分开；
3. 保存数据带 schemaVersion，方便以后迁移；
4. 所有字段给出类型、默认值和用途；
5. AIResponse 必须能被 JSON.parse 稳定解析；
6. 指出哪些字段绝不能交给 AI 直接覆盖。
```

这一阶段很重要。先把“游戏记住什么”设计好，再做页面，否则后期加入存档和剧情旗标会非常痛苦。

### 第四步：要求 AI 搭建 MVP

```text
现在实现第一版可运行 MVP。请严格限制范围：

页面：标题页、API 设置页、创建角色页、主游戏页、对话弹窗、存读档页。
系统：四段时间、五个地点、两名角色、三个关系阶段、体力、最近记忆、一个任务事件。
互动：三个 AI 生成选项 + 玩家自由输入。
技术：原生 HTML/CSS/JavaScript，手机端优先，无框架。

工程要求：
- index.html 只放页面骨架；
- CSS、状态、数据、AI 调用、系统逻辑分文件；
- 不把 API Key 写死在源码；
- 所有 AI 返回先校验再进入状态；
- 请求失败、超时、JSON 错误时显示可恢复提示；
- 提供一个不调用 API 的模拟模式用于测试；
- 每完成一个文件，说明它负责什么以及如何验证。

验收标准：新建游戏后可以移动、对话三轮、结算一次状态、推进时间、保存并刷新后读取；手机宽度 390px 下不能横向溢出。
```

### 第五步：把系统提示词与业务逻辑分开

给 AI 的运行时提示词，建议按模块拼接：

```text
[世界规则]
[当前场景事实]
[角色卡]
[关系阶段规则]
[玩家资料与玩家主体性规则]
[相关记忆]
[本轮用户输入]
[输出 JSON 协议]
```

不要每次都把全部世界设定、全部角色卡和全部历史发进去。当前和谁对话，就只发送这名角色需要知道的信息。

一个简化版对话输出协议可以是：

```json
{
  "action": "不超过40字的可观察动作",
  "dialogue": "角色台词",
  "translation": "外语台词的中文翻译，没有则为空字符串",
  "options": [
    {"type": "warm", "text": "温和但不保证加好感的选择"},
    {"type": "sharp", "text": "直接或质疑的选择"},
    {"type": "probe", "text": "观察或试探的选择"}
  ],
  "proposedEffects": {
    "affectionDelta": 0,
    "memoryFact": "本轮值得记住的客观事实"
  },
  "endConversation": false
}
```

注意这里叫 `proposedEffects`，也就是 AI 只“建议”变化。代码还要把好感变化限制在允许区间，并检查事件条件，不能让 AI 返回“金钱加一百万”就直接生效。

### 第六步：一次只改一个问题

不要对 AI 说“现在有很多 bug，你全部修好”。更有效的报错格式是：

```text
预期：第三轮对话结束后只推进一个时间段，并保存最后一条记忆。
实际：界面关闭了，但时间推进两次，记忆重复写入。
复现：新建游戏 → 进入休息区 → 连续选择三次对话选项。
控制台错误：无。
相关文件：[文件名与函数]

请先定位根因，只修改与重复触发有关的代码。不要重写 UI，不要改变数据结构。修改后说明测试步骤。
```

AI 最怕的是边界模糊。你越清楚地描述预期、实际、复现步骤和允许修改范围，它越容易稳定修好。

## 第八部分：系统提示词怎么写才不容易 OOC

好的提示词不是越长越好，而是优先级清楚、能被检查。

建议按下面顺序：

1. **任务定义**：你正在扮演谁，当前要完成什么；
2. **事实边界**：当前时间、地点、在场人物、已发生事件；
3. **角色行为逻辑**：价值排序、压力反应、语言风格；
4. **关系阶段**：当前能表现到什么程度；
5. **玩家主体性**：不能代替玩家思考、说话或行动；
6. **内容边界**：禁止事项与同意规则；
7. **输出格式**：必须返回什么字段、字数和数值范围。

还可以加入生成前自检：

```text
生成前静默检查：
1. 这段反应是否来自该角色的价值观，而不是通用恋爱模板？
2. 是否错误替玩家决定了情绪、台词或动作？
3. 当前关系阶段是否允许这种亲密程度？
4. 台词若换成另一角色是否仍然完全成立？若是，重写。
5. 是否与当前地点、时间、任务和已知记忆冲突？
6. 最终只输出合法 JSON，不输出检查过程。
```

### 提示词常见反效果

- **形容词堆太多**：冷漠、腹黑、温柔、疯批同时出现，却没有触发条件；
- **示例台词太多**：模型反复复读示例，角色像口头禅机器；
- **禁止词过多但没有替代方向**：模型只知道不能写什么，不知道冲突应该怎么写；
- **全员共享一套恋爱规则**：最后所有角色表达方式都一样；
- **要求“永远正确”**：角色失去缺点，也就失去剧情；
- **让 AI 管全部数值**：状态漂移、存档污染，难以修复。

## 第九部分：从《里世界》可以借鉴和继续优化的地方

《里世界》的项目结构已经体现出很好的模块化思路：总入口管理多个游戏；每个游戏再把样式、核心状态、系统、API 和静态数据拆开。以平行世界模块为例，角色与地点属于数据层，时间和存档属于核心层，对话、关系、地图、论坛、悬赏属于系统层，模型请求则单独放在 API 层。

这种拆法的好处是：改角色不会碰存档，改界面不会误伤提示词，新增任务也不必把所有代码塞进一个 HTML 文件。

其中尤其值得保留的设计有：

- 多阵营共处的平行世界前提，解决不同作品角色同场问题；
- 地点与角色状态绑定，让人物存在于世界而不是通讯录；
- 关系阶段与好感结合，控制感情节奏；
- 温、锐、暗三方向选项加自由输入，兼顾引导与自由；
- 最近互动和世界事件摘要，帮助角色延续记忆；
- 任务、论坛、悬赏等非恋爱内容，支撑群像和生活感；
- 样式、数据、系统和 API 分离，方便继续维护。

如果从教学版继续优化，我建议优先做下面几件事：

1. 为 AI 返回增加严格字段校验和默认回退，避免格式错误让页面卡死；
2. 保存数据加入版本号和迁移函数，后续加字段时旧存档仍能读取；
3. 把静态角色资料和运行时角色状态彻底分离，避免意外修改原始角色卡；
4. 用“数字 + 关键旗标”共同控制关系事件；
5. 给每个角色单独做 OOC 测试集；
6. 增加模拟响应模式，不消耗 API 就能测试完整流程；
7. 正式公开部署时使用服务端代理保存密钥，不要让长期密钥暴露在浏览器前端或公开仓库。

最后这一点非常重要。纯前端页面直接请求模型接口，虽然适合个人本地使用和快速原型，但部署到公开网站后，浏览器中的请求方式与密钥管理必须重新考虑。不要把自己的 API Key 写进 JavaScript 再上传 GitHub，也不要把含密钥的配置文件提交到仓库。公开发行时，应使用有鉴权、限额和滥用保护的后端代理；如果只是让玩家自行填写密钥，也要明确说明它存在哪里、会被发送到哪里，并提供清除方法。

## 第十部分：测试不是最后一步，而是边做边测

### 功能测试

- 第一次打开能否正常创建角色；
- 不填写必填项时是否有明确提示；
- API 请求失败后能否重试，而不是死锁；
- AI 返回代码块、缺字段或非法 JSON 时是否有回退；
- 连续快速点击会不会重复扣体力或重复推进时间；
- 存档后刷新页面，时间、位置、关系、事件旗标是否一致；
- 旧存档遇到新版本字段时能否补默认值；
- 390px 手机屏幕是否出现按钮遮挡或横向滚动。

### 角色测试

让每个角色都回答同一组场景：

1. 玩家第一次迟到；
2. 玩家任务中受伤并隐瞒；
3. 玩家公开质疑他的判断；
4. 玩家向另一个阵营求助；
5. 玩家明确拒绝亲密接触；
6. 两人刚认识与已经信任时分别处理同一件事。

检查语言、价值选择和关系边界是否不同。不要只看台词“苏不苏”，要看人物是否一致。

### 剧情测试

- 证据不足时 AI 有没有提前揭晓真相；
- 玩家跳过事件时，后续是否错误认为已经完成；
- 两条支线是否写入互相矛盾的事实；
- 角色不在场时是否知道不该知道的信息；
- 玩家失败后是否存在继续游戏的路径；
- 恋爱进展是否由一次高额好感变化突然跳级。

可以把测试结果继续交给 AI，但要提供完整复现信息。让 AI 先解释根因，再允许修改，通常比直接要求“优化一下”可靠。

## 第十一部分：适合新手的制作顺序

如果你是第一次做，按这个顺序最省力：

1. 写一句话概念与最小企划表；
2. 只选两名角色，完成可执行角色卡；
3. 设计五个地点、四个时间段和一个事件；
4. 定义玩家身份与最少状态字段；
5. 写清 AI 输入模块和 JSON 输出协议；
6. 让 AI 先做无美术的 MVP；
7. 用模拟响应跑通移动、对话、结算、时间和存档；
8. 接入模型 API，测试错误恢复；
9. 做角色一致性和剧情旗标测试；
10. 最后才扩展人物、论坛、商店、短信、任务和视觉效果。

不要一开始就做十名男主、几十个地点、复杂战斗、论坛、朋友圈、商店和多结局。第一版真正的目标不是“内容很多”，而是完成一次可重复、可存档、不会崩的游戏循环。只要这个骨架稳定，增加内容只是逐层扩建。

## 结尾口播

以上就是一个 COD 乙女向 AIRP 文游从构思到落地的基本流程。

简单总结一下：先确定玩家究竟要体验什么，再把世界观写成规则，把角色性格写成行为逻辑，把剧情写成可以触发的事件；让代码管理确定的状态，让 AI 负责有变化的表达。和 AI 沟通时，也不要只说“帮我做一个游戏”，而要给它明确的上下文、任务边界、输出格式和验收标准，然后一轮一轮地做、小范围地改、持续地测。

AI 可以帮我们降低实现门槛，但作品真正的方向、审美、边界和取舍，仍然来自创作者本人。工具能替我们写代码、整理资料和发现问题，却不能替我们回答“为什么要做这个故事”。

希望这期教程能帮大家把脑海里的世界真正做出来，也希望大家都能在创作里找到属于自己的快乐。
